# 로컬 동시 이동 측정

이 문서는 초기 전체 스냅샷과 최적화 프로토콜의 개발용 측정 결과를 남깁니다. 정식 서비스의 수용 인원이나 인터넷 성능을 보증하지 않습니다.

## 재현 방법

Node.js 24 이상에서 의존성을 설치한 뒤 저장소 루트에서 실행합니다.

```sh
npm ci
node scripts/load-test.mjs
```

스크립트는 실행 중인 개발 서버를 사용하지 않습니다. 별도 자식 프로세스에 `createGameServer({ dbPath: ':memory:', port: 0 })`로 임시 서버를 시작하고, 부모 프로세스에서 실제 WebSocket 클라이언트 108개를 같은 채널에 연결합니다. 모든 접속이 끝난 뒤 1초 기다리고, 10초 동안 각 클라이언트가 초당 약 10회 이동 목표를 전송합니다. 모든 플레이어가 서로의 관심 반경에 들어오는 25유닛 이내 목표를 사용합니다. 종료 시 연결과 임시 서버를 정리합니다.

다음 항목은 실패 가능한 검사입니다.

- 108명 모두 프로토콜 오류나 연결 종료 없이 유지됩니다.
- 108명 각각 서버 권한 이동으로 시작점에서 3유닛 이상 움직입니다.
- 각 클라이언트가 10초간 최소 50회의 월드 갱신을 받습니다.

스크립트는 메모리 DB를 사용합니다. 지속 디스크 쓰기, 장시간 운영, 공동 수행·채집 부하, 브라우저 렌더링, 원격 네트워크, TLS 프록시는 이 측정에 포함하지 않습니다. 가입과 종료 때 발생하는 명단 전송은 측정 구간 전후에 일어나므로 이동 중 전송량과 구분해야 합니다.

## 초기 프로토콜 1 측정

측정일: 2026-11-02. Linux x64, Node.js v24.19.0, AMD EPYC 9V74가 표시되는 공유 개발 환경에서 실행했습니다. 프로세스가 확인한 병렬 실행 가능 CPU 수는 4입니다. 같은 머신의 다른 개발 작업을 완전히 격리하지 않았으며 반복 결과는 달라질 수 있습니다. 서버와 클라이언트는 서로 다른 Node.js 프로세스입니다.

| 항목                                        |            관측값 |
| ------------------------------------------- | ----------------: |
| 동시 이동 클라이언트                        |             108명 |
| 측정 시간                                   |          10,000ms |
| 수신 월드 프레임 합계                       |          10,692회 |
| 클라이언트당 최소 프레임                    |              99회 |
| 서버 갱신 간격 p50 / p95 / 최대             | 100 / 104 / 118ms |
| 서버 시각 → 로컬 수신 지연 p50 / p95 / 최대 |   17 / 53 / 147ms |
| 전체 월드 JSON 전송량                       |       22.87MiB/초 |
| 서버 RSS / 측정 중 최대 RSS                 |    68.0 / 68.2MiB |
| 측정 구간 서버 CPU 사용 시간                |           2.767초 |
| 프로토콜 오류 / 연결 종료                   |           0 / 0건 |

갱신 간격은 각 메시지의 서버 시각 차이이며 수신 지연과 다릅니다. 서버와 클라이언트가 같은 호스트의 시계를 사용하는 조건입니다. 전송량은 모든 클라이언트가 받은 월드 JSON 바이트의 합계로, WebSocket·TCP 헤더를 포함하지 않습니다. CPU 사용 시간은 경과 시간과 다르며 서버 프로세스만 측정합니다.

초기 프로토콜 1의 전체 스냅샷은 이름·염주·띠 등 잘 변하지 않는 데이터도 10Hz로 반복합니다. 중앙 광장에 108명이 모이면 이 대역폭이 중요한 비용이 됩니다. 이 결과만으로 10개 채널 총 1,080명의 운영 성능을 주장할 수 없습니다.

## 프로토콜 최적화 비교

동일한 108명 대표 데이터를 JSON으로 직렬화해 크기만 비교하면 다음과 같습니다. 아래는 실제 부하 재측정이 아닌 메시지 형태별 계산입니다.

| 형태                                                | 대표 프레임 크기 | 초기 대비 감소 |
| --------------------------------------------------- | ---------------: | -------------: |
| 전체 플레이어 객체와 채집 지점 정의                 |          22,431B |              — |
| 변하는 플레이어 필드와 채집 지점 상태만 객체로 전송 |          10,818B |          51.8% |
| UUID를 유지한 이동 튜플                             |           6,714B |          70.1% |
| 임시 숫자 식별자를 쓰는 이동 튜플                   |           2,824B |          87.4% |

최적화 프로토콜 2가 있는 버전에서는 다음 명령으로 같은 측정을 실행할 수 있습니다.

```sh
PROTOCOL=2 node scripts/load-test.mjs
```

프로토콜 2는 변경 시 전송하는 `roster` 명단과 10Hz의 `frame` 상태를 분리합니다. 스크립트는 `frame`과 측정 중 발생한 `roster` 바이트를 각각 보고하고 합계도 출력합니다. 프로토콜 1은 부하 스크립트의 기본값으로 유지해 비교가 가능합니다. 게임 클라이언트는 프로토콜 2를 요청합니다.

## 최종 코드의 프로토콜 1·2 실측 비교

같은 날짜와 환경에서 최종 서버 코드로 각각 10초씩 다시 측정했습니다. 최종 코드는 두 프로토콜 모두 채널·틱별 공개 데이터 계산과 동일 가시 목록의 직렬화 결과를 재사용합니다. 따라서 아래 프로토콜 1의 CPU 결과는 그 최적화가 없던 초기 측정과 다릅니다.

| 항목                            |        프로토콜 1 |        프로토콜 2 |
| ------------------------------- | ----------------: | ----------------: |
| 접속 인원                       |             108명 |             108명 |
| 실제 이동 메시지 처리율         |      1,069.1회/초 |      1,069.1회/초 |
| 측정 시간                       |          10,001ms |          10,001ms |
| 월드·프레임 수신 합계           |          10,692회 |          10,800회 |
| 클라이언트당 최소 프레임        |              99회 |             100회 |
| 갱신 간격 p50 / p95 / 최대      | 100 / 102 / 107ms | 100 / 101 / 102ms |
| 로컬 수신 지연 p50 / p95 / 최대 |     8 / 19 / 56ms |      2 / 4 / 23ms |

| 측정 중 명단 전송량             |         해당 없음 |           0MiB/초 |

동일한 안정된 108명 이동 군집에서 프로토콜 2의 월드 JSON 전송량이 약 90.0% 감소했습니다. 이 구간에는 입퇴장·이름 변경·장비 변경이 없어 명단을 다시 보낼 일이 없었습니다. **최초 입장 명단은 측정 시작 전에 전송됐으므로 이 전송량에 포함되지 않습니다.** 새로운 참가자나 가시 범위·이름·장비 변경이 많은 상황에서는 `roster` 전송량이 추가됩니다. CPU와 지연 수치는 공유 환경에서 한 번씩 얻은 관측값으로, 통계적 성능 보장은 아닙니다.

## 후속 검증 범위

실제 출시에 앞서 외부 클라이언트·지속 DB·108명 동시 수행·장시간 재접속·10개 채널 동시 부하를 별도로 검증해야 합니다. 클라이언트에는 가까운 20명(모바일 12명)을 상세 표시하고 나머지 플레이어를 인스턴싱하는 LOD를 적용했습니다. 독립 Chromium의 합성 108명 장면에서는 그리기 호출이 1,676회에서 448회로 줄었습니다. 이는 실제 108개 브라우저의 동시 접속 시험이 아니므로, 서버 전송 시험과 별도로 실제 기기의 WebGL 프레임 시간과 장시간 군중 장면을 측정해야 합니다.
